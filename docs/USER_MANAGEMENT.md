# People & access

Sign in at the local application (`http://127.0.0.1:8788`) using Workspace password sign-in. The requested temporary administrator is `admin.72bpm`; the secret is delivered separately, never committed or bundled. It expires after 24 hours. First sign-in opens Set your own password. Enter the temporary/current password and a unique new password of 14–200 characters, then sign in again. This account belongs only to the current local runtime, not the public Sites demo or another installation.

Administrators land in People & access. Create user asks for a unique immutable account ID, display name, explicit role, permitted business departments and an approval/reason. Request reviewers additionally require Accounts, Software or R&D as their functional team. The role description explains the resulting access. New local users receive a randomly generated temporary password displayed once. Share that secret privately through the approved channel; it cannot be retrieved later. Use Credentials → Issue temporary password if it was lost. Refreshing/leaving/dismissing the one-time panel clears it. There is no automatic email delivery.

Edit updates name, role, team, department grants and active status. Saving revokes the affected user's sessions. Stale edits return a conflict and require refreshing the directory. Self-role/status/removal operations are blocked; another administrator must make those changes. Credential actions include resetting local passwords, revoking sessions, linking/replacing an independently verified Google subject and removing a Google binding. Linking requires explicit verification confirmation and an approval reference. Existing Google subject values are not displayed in the directory. Production passwords and MFA are managed through Google Workspace; local password creation/reset is disabled in production.

Remove revokes access, invalidates the password and clears Google bindings and sessions while preserving agreement ownership and audit history. Removed accounts remain in the Removed accounts filter. Restore returns the same account to a disabled state without restoring credentials. Review role/departments, activate and issue or link credentials before the employee signs in again. Use a fresh account ID for a different person. Legal contract erasure is a separate process; account removal does not delete contracts.

Access history shows account-related changes with actor and server timestamp. It does not grant document-history access. Password values, hashes and salts are never returned by the directory or logged. The UI includes search, current/removed/all filters, counts and responsive cards. The original legacy SQLite runtime does not provide these new administrator APIs; use the canonical PostgreSQL runtime.

Upgrade existing production installations with migration 2 and reapply `production/runtime-grants.sql` for `account_controls`, then restart. Development applies migrations automatically. Back up the existing database and key before an upgrade. No source package contains runtime accounts or plaintext credentials.

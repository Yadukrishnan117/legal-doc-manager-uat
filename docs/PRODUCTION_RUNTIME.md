# ChargeMOD production runtime — 5 November 2026

The new `production/` runtime implements PostgreSQL persistence, department/assignment RBAC, durable cookie sessions and OIDC handshakes, private S3/KMS document storage, synchronous ClamAV checks, transactional workflow updates, row locking and revision conflicts. It serves the redesigned login and role-specific workspace from `backend/public/`. It is separate from the static Sites demo. No cloud resources, real staff accounts, OAuth credentials or production data have been created.

## Run and verify locally

Install Node.js 24.12+ and run `npm ci`, then `npm run test:all`. `NODE_ENV=development DEV_PASSWORD_LOGIN=1 npm start` starts the new application on `http://127.0.0.1:8788`. Embedded PostgreSQL/PGlite and encrypted files persist under ignored `production/.runtime/`. No accounts are seeded. Development scanning is a limited fixture check and must never be used with real documents. Development binds only to loopback.

Provision approved named development accounts with `NODE_ENV=development npm run user:production`, supplying a JSON record through protected stdin: `id`, `name`, `role`, `departments`, `password`, optional `team` for request reviewers. Account IDs accept letters, digits, `@._-`. A password must be unique and 14–200 characters. Do not put passwords in command arguments, source control or chat. Create distinct Legal Manager, Sales and Operations accounts in the same permitted department so request assignments are valid. Administrators have no default agreement access.

The previous SQLite implementation remains available via `NODE_ENV=development DEV_PASSWORD_LOGIN=1 npm run start:legacy` on port 8787, with its original setup/provision commands. Its records are not automatically copied into PostgreSQL. Do not point the two runtimes at the same runtime directory.

## Deploy the authenticated application

1. Provision private Mumbai PostgreSQL, private S3 with all four public-access blocks, a configured KMS key ARN, an internal ClamAV service with current definitions, and container compute behind an HTTPS load balancer. The existing CloudFormation file is an undeployed data foundation, not complete infrastructure. Runtime traffic needs network access to Google OAuth/JWKS and approved AWS endpoints.
2. Use a migration owner and a distinct restricted runtime DB login. Run `node production/manage.ts migrate` with `MIGRATION_DATABASE_URL` and `DATABASE_CA_FILE` in a trusted operator environment; the CA must verify the actual database certificate. Apply `production/runtime-grants.sql` after creating `ldm_runtime`. Do not give the application migration credentials. Startup rejects superuser/BYPASSRLS and table-owning runtime accounts. It checks migrations 1 and 2. Existing deployments must apply migration 2 with the owner, then reapply runtime grants for the new account-control table before restarting. RLS derives the fixed ChargeMOD organization from server configuration, never browser input.
3. Supply the names in `production/.env.example` through the company's secret manager. `LDM_DATA_KEY` is an application encryption key in addition to S3 SSE-KMS. Preserve it separately with controlled backup access; rotation requires re-encryption, so do not replace it blindly. Give the task role only designated prefix `chargemod/objects/*`, required bucket readiness reads, and the corresponding KMS permissions. No public or presigned file URLs are issued: every download is authorized and streamed by the server.
4. Create an internal Google Workspace OAuth client with exact callback `APP_ORIGIN/auth/google/callback`, domain `chargemod.com`, and company-approved MFA/device policy. The app verifies signed tokens through `jose`, issuer, audience, authorized party, nonce, verified email, exact hosted domain and token lifetime. PKCE and five-minute encrypted, shared database state protect the handshake. A domain hint never grants a role.
5. Provision each production user with `NODE_ENV=production node production/manage.ts user` through protected stdin. Include an independently verified `googleSubject` and explicit role/departments. The command generates an unknown random password; production has no password sign-in path. No email auto-linking, default admin, public signup or role selector exists. For approved role/department changes use `node production/manage.ts access` with `id`, `role`, `departments`, `active`, optional reviewer `team`, and the approved `reason` through protected stdin. It validates grants, records the change and revokes all sessions atomically; the administrator dashboard also supports audited creation, editing, role/department grants, removal/restoration, session revocation and verified identity binding. Self-access changes remain blocked. See `docs/USER_MANAGEMENT.md`.
6. Build the Dockerfile and run with read-only application filesystem, approved CA mount, workload identity/secret injection and `NODE_ENV=production`. Replace the rolling base image tag with a reviewed digest in the release pipeline. Expose only the load balancer, preserve the exact configured Host, and use health paths `/health/live` and `/health/ready`. Readiness verifies DB access; S3 policy/region/encryption and scanner readiness are checked at startup. Add external continuous scanner, storage and OAuth monitoring before launch. Direct database/ClamAV ports must not be public.
7. Verify actual RDS TLS connections, IAM allow/deny, bucket/KMS readiness, current ClamAV definitions, live company SSO, revocation, concurrent updates across two application instances and backup restoration in staging. The automated suite uses embedded PostgreSQL and protocol fixtures; it does not establish that your AWS/Google configuration is correct.

The container handles graceful shutdown and bounded request, database and scanning timeouts. Cookies are HttpOnly/SameSite Strict, Secure on HTTPS; sessions expire after eight hours absolute and thirty minutes idle. Mutations require exact Origin and CSRF token. Login failures consume shared database rate limits even when workflow transactions roll back. The initial rate limiter uses the actual peer address; behind a shared proxy, deploy an approved per-client edge limiter and tune the conservative shared limit. No arbitrary forwarded IP header is trusted.

## Workflow and concurrency

Legal uploads and publishes a common master; Sales records a closed lead, uses the currently selected published version and prepares a separate client copy. Only TXT placeholder assembly and PDF reference downloads are supported. Word/PDF generation is still future work. Client changes require Legal revision and explicit sharing. Exact current-version confirmation, separate manager approval and explicit final release precede Operations execution. Printing, dispatch, original-scan receipt and Legal verification remain separate recorded actions.

Agreement upload/actions require `revision` from the most recent record. A stale write returns 409 and the user must refresh. Master publication/withdrawal requires its current `version`; starting a client copy requires its selected `templateVersion`. PostgreSQL row locks serialize updates and library starts. Sequence numbers prevent concurrent count-based ID collisions. Lead/template starts have unique keys and request fingerprints. DB transactions commit before success reaches the browser; failures roll back workflow changes. Upload scanning and immutable encrypted object writes happen before document metadata commits. A failed database transaction may leave an unreferenced object: review reconciliation before any purge. Do not add automatic expiry that could remove held contracts.

## Privacy and operating limits

This is an implementation, not a legal compliance certification. Retain the existing company policy drafts and India privacy applicability review. Public grievance contact, lawful bases, contractual retention, processor/vendor flows, incident ownership, signed policies and phased DPDP applicability require company approval. Keep government IDs and unrelated sensitive personal data out of uploads. Internal privacy requests do not automatically erase contracts; legal hold and retention guard deletion proposals, and no destructive purge exists.

Configure India-based centralized security logging and the applicable CERT-In reporting/retention process. Database audit events are append-only to the runtime role, but DB owners retain administrative powers; external immutable log shipping is not implemented here. Request failure logs omit documents, tokens, cookies and payloads. Security logs and contract retention are distinct. Back up PostgreSQL, private object versions and the application key; complete an isolated restore drill before production data. Verify all vendor/support/telemetry flows separately: selecting Mumbai does not establish end-to-end data residency.

CRM remains unconnected: manual closed-lead entry is available. Legacy signed event receipts and outbox records are scaffolding; no automatic mapping, delivery/retry worker, client email, e-signature provider or billing system is active. Single company staff UX is intentional. Organization-aware RLS is groundwork, not a finished multi-company SaaS offering.
